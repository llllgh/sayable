# Level 4 AI 角色扮演对话模式设计

> 状态：已实现首版
>
> 前置能力：表达骨架、`trigger`、固定复习阶梯、语音输入、模型判卷

## 1. 目标

Level 4 不再直接告诉用户“现在要表达什么”，而是让 AI 扮演客户或同事，在短对话中制造某个表达的 `trigger`，检验用户能否自然识别沟通机会并调用对应骨架。

它补齐现有训练链路中的最后一段：

`英文提示下造句 -> 中文意图召回 -> 新场景迁移 -> 对话中识别 trigger 并主动产出`

Level 4 不是开放式聊天，也不替代真实使用。条目是否“已掌握”仍由现有规则决定：复习阶梯达到要求，并有足够的真实使用记录。

## 2. 产品边界

### 2.1 做什么

- 每次只训练一个目标骨架。
- AI 根据条目的 `trigger`、用户画像和已有例句生成一个新场景。
- AI 不显示目标骨架、中文释义、trigger 文本或参考答案。
- 对话控制在 2 个用户回合、2 到 4 分钟内。
- 评价用户是否识别了沟通意图，以及表达是否正确、清晰、简洁。

### 2.2 不做什么

- 不做无限回合的通用英语陪练。
- 不要求逐字复现数据库中的例句。
- 不因为用户选择了其他同样有效的表达而判错。
- 不把 style optimization 自动加入长期复习。
- 不自动监听或分析真实会议，也不实现 Level 5 的“自由表达自动检测”。
- 不改变 `0 / 1 / 3 / 7 / 21 / 60` 的调度间隔。

## 3. 进入条件

通过纯函数 `roleplayEligibility(item)` 判断是否显示入口：

- `item.box >= 3`，用户已经完成无英文提示的召回。
- `item.trigger` 非空。
- 条目未归档。
- 文本模型已连接且设备在线。

Level 4 首版作为句库详情和到期复习后的可选入口，不自动替换普通复习。这样可以先验证训练价值和成本，再决定是否纳入默认调度。

## 4. 单次交互

### 4.1 开场

界面只显示角色和一句客户发言，例如：

> 客户 CTO：我们想一次覆盖 20 个部门，但治理风险让我有些担心。

用户不知道系统正在考察哪个表达，只能根据对话判断应采取的沟通动作。

### 4.2 第一轮回答

用户用语音或文字回答。模型只做内部判断，不立即展示纠错，以免打断对话。如果用户尚未面对目标 trigger，模型必须继续制造机会，不能提前判失败。

### 4.3 追问

AI 根据用户回答给出一次自然追问，例如：

> 如果先试点，你建议从多大范围开始？

追问必须保持角色一致，并允许用户补充或修正策略。

### 4.4 结束反馈

第二轮回答后结束，不继续闲聊。反馈按以下顺序展示：

1. **是否抓住时机**：是否识别了 trigger 对应的沟通需求。
2. **是否完成意图**：即使没使用目标骨架，是否有效完成沟通任务。
3. **目标骨架**：是否自然使用，槽位关系是否正确。
4. **Correct**：是否存在 blocking error 或 recurring grammar error。
5. **Clear**：对方是否能立即理解结论和行动建议。
6. **Shorter**：仅在确实能明显压缩时给一个更短版本。

style optimization 只作为即时建议显示，不创建条目、不进入长期队列。

## 5. 判定与调度

首版采用保守规则：

- `roleplay_pass`：识别 trigger、完成沟通意图，且没有 blocking error。
- 使用目标骨架不是唯一通过条件；若用户用了同样有效的替代表达，应判“沟通通过，但本次未练到目标骨架”。
- 只有 `roleplay_pass && used_target` 才记为一次目标骨架的 Level 4 成功。
- Level 4 成功可按一次普通复习成功推进阶梯。
- Level 4 失败不降级，只安排一次普通召回在 8 小时后重试。
- Level 4 记录不能替代 `usedReal`，不能单独把条目标记为“已掌握”。

该不对称规则避免更难的训练模式破坏已经建立的记忆进度。

## 6. 数据契约

在不改变现有 `item` 主结构的前提下，使用独立会话记录：

```ts
interface RoleplaySession {
  id: string;
  itemId: string;
  startedAt: number;
  completedAt: number;
  scenario: string;
  role: string;
  turns: Array<{
    speaker: 'ai' | 'user';
    text: string;
    at: number;
  }>;
  result: {
    triggerRecognized: boolean;
    intentAchieved: boolean;
    usedTarget: boolean;
    issueLevel: 'none' | 'minor' | 'blocking';
    clear: boolean;
    concise: boolean;
    verdict: string;
    fix: string | null;
    tighter: string | null;
  } | null;
}
```

会话单独持久化，避免把多轮对话塞入 `item.history`。`item.history` 只追加一条摘要记录，用于调度和统计。

## 7. 模型调用

每次最多三次结构化调用：

1. `roleplay.start`：根据画像、trigger 和条目生成角色、场景和开场白。
2. `roleplay.continue`：读取第一轮回答，生成一次追问，同时判断目标机会是否已经出现。
3. `roleplay.judge`：对两轮回答做最终判定。

硬性约束：

- 提示词中可包含目标骨架，但 AI 的角色发言不得泄露它。
- 不得虚构具体客户名、公司机密、项目数据或故障。
- 输出必须通过独立 Zod schema；不合规则快速失败。
- 日志只记录任务类型、耗时和 token，不记录对话正文。
- 离线或模型失败时明确回退到普通召回，不伪造角色扮演结果。

## 8. UI

- 入口文案：`情境对话`
- 开始前不展示教学说明，只显示角色、场景和第一句发言。
- 对话区使用紧凑消息列表，不做聊天应用式装饰。
- 底部固定语音/文字输入和发送按钮。
- 最多两次用户回答；第二次提交后自动进入反馈。
- 反馈完成后仅保留 `完成`、`再练一次`、`记录实际使用` 三个动作。

## 9. 验收指标

实现前先准备 20 个真实工作 trigger 作为评测集。首版验收：

- 95% 的开场不会直接泄露目标骨架或答案。
- 90% 的场景确实制造了目标 trigger。
- 有效替代表达不会被误判为 blocking。
- 单次会话严格不超过 2 个用户回合和 3 次模型调用。
- 任意失败都不会丢失用户回答或错误推进复习阶梯。
- 连续使用两周后，再决定是否把 Level 4 纳入默认到期复习。

## 10. 实施里程碑

- **M1 数据与评测（已完成）**：定义三个 Zod schema、会话存储、状态转换和泄露检测测试。
- **M2 对话引擎（已完成）**：实现 start / continue / judge，覆盖泄露检测与替代表达判定。
- **M3 产品入口（已完成）**：接入句库详情和复习完成页，完成文本与语音交互。
- **M4 小流量验证（待真实使用）**：本地全流程、真实模型回归、Android 模拟器与真机走查。

每个里程碑单独验收；M4 通过前，不把 Level 4 设为默认复习方式。
