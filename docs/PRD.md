# 说得出 Sayable · 产品需求文档（PRD）

> 版本 v1.0 ｜ 2026-08-31 ｜ 单用户优先，作者即第一用户
> 配套文档：`MVP-TODO.md`（近 4 周清单）、`ENGINEERING.md`（架构 / 数据 / 契约）

---

## 1. 问题陈述

目标用户：英语已能读懂、能开会、但**没有整块学习时间**的专业人士。

真实症状（不是猜的，是用户原话）：

1. 听到一个很好的表达，当时觉得好，几分钟后就过去了。
2. 真正开口时，还是调用最熟的简单词和中文式组织。
3. 为了把意思说完整只能不断补充修正，因此显得啰嗦。
4. 新词「认识」，说话时检索不到。
5. 没有稳定的每天一小时，传统计划一定崩。

**误诊与正诊**：

- ❌ 误诊：输入不够 → 解法是背更多词、听更多材料、每天保证 1 小时。
- ✅ 正诊：**passive vocabulary 很大，但 active vocabulary 的调用通道太窄**。缺的是「检索—重组—复用」的次数，不是知识量。

由此推出产品定位：

> **不是一个英语学习 App，是一个让「听懂的表达」变成「说得出的表达」的个人管道。**

单位不是「今天学英语了吗」，而是「今天有没有遇到值得收编的表达」。

## 2. 核心命题与不可让渡的原则

**命题**：学习单元既不是单词也不是整句，而是**可复用的表达骨架**。

```
听到：The bottleneck has shifted from generation to verification.
收的不是这句话，而是：The bottleneck has shifted from X to Y.
再迁移到你自己的场景：
  The bottleneck has shifted from writing code to reviewing it.
  The bottleneck has shifted from data collection to labeling quality.
```

六条原则，后续任何功能决策都不能违反：

| # | 原则 | 具体含义 |
| --- | --- | --- |
| P1 | **捕获路径零阻力** | 捕获时不分析、不联网、不提问、不评分。存下就走，2 秒完成。念头是一闪而过的，任何一道门都会杀死它。 |
| P2 | **出门税，不是进门税** | 所有认知负担（答题、造句、判卷）都放在用户**已经处理完一条**、注意力已经在场时，用「顺手一题」的方式邀请，且永远可跳过。 |
| P3 | **抽象优先于收藏** | 任何一条原文进库前必须产出带槽位的骨架。存原句不算学习，存骨架才算。 |
| P4 | **每周硬预算 3 条骨架** | 收编要限量，防止退化成收藏癖。**闪存不限量**——限的是「进入学习序列」的数量。 |
| P5 | **只有真实使用才能毕业** | 模型判分不能单独授予「已内化」。必须有一次真实场景使用打卡（会上说了 / 邮件写了 / 跟人聊时用了）。 |
| P6 | **一次只给一个骨架** | 模型输出严格限一个主骨架。给三个等于给零个。 |

## 3. 用户旅程

### 3.1 主循环（每天，总计 < 5 分钟）

```
① 闪存（随时，2 秒）
   听到 / 说得不满意 / 想表达但卡住 → 存原文，什么都不做
        ↓
② 处理（有 3 分钟时，或通知提醒时）
   打开待处理 → 模型分析 → 得到骨架 + 为什么好 + 你的场景例句
   → 立刻用它造 2 句（这是第一次主动产出，不可省略）
        ↓
③ 出门税（处理完顺手）
   随机抽一道到期题作答 → 可跳过
        ↓
④ 隔日召回（本地通知推来）
   不看答案，先努力想 → 想不起来 → 再看到答案
   （想不起来的那一下才是记忆形成的地方，不是「再看一遍」）
        ↓
⑤ 真实使用打卡
   真的在会上/邮件里用了 → 打卡 → 累计 3 次 → 标记「已内化」
```

### 3.2 四个入口（对应用户最初提的三个场景 + 画像驱动）

| 入口 | 输入 | 输出 |
| --- | --- | --- |
| **译写** | 一段中文 | 自然英文示例（不是直译）+ 标出值得学的骨架 + 要求跨场景造句 |
| **改写** | 自己的英文 | 改进版 + **为什么这样更好**（要指出具体的中文思维习惯）+ 提取骨架入库 |
| **衍生** | 自己学到的表达 | 抽象成骨架 + 一组同族迁移用法 + 结合你的画像给例句 |
| **压缩台** | 一段啰嗦的英文 | 保留逻辑 → 压缩到约一半长度 → 提炼 1~2 个 reusable pattern |

> 「压缩台」是老师建议里最被低估的一条：**啰嗦不完全是英语问题，是信息密度高 + 想把限定条件全交代清楚**。所以压缩要作为一等功能，而不是改写的附属。

### 3.3 画像驱动（Profile）

原方案的 profile 只有 `display_name / native_language / target_language / english_variety / default_tone / typical_domains`——太轻，生成的例句会泛泛而谈。

必须采集（都是可选，但每填一项例句质量都提升）：

- 岗位与在做的事（一句话，自由文本，比枚举有用得多）
- 常打交道的对象（同事 / 客户 / 面试官 / 老外老板）
- 高频真实场景（周会同步、方案评审、跨时区对齐、给上级汇报、面试、社交寒暄）
- 最近一次说得不满意的场合（用于冷启动）
- 想要的语域（务实简洁 / 有分量 / 亲和）
- 明确不要的风格（黑名单，随用随加）

## 4. 功能需求

### 4.1 P0（MVP 必须有，缺一个闭环就不成立）

| ID | 功能 | 验收要点 |
| --- | --- | --- |
| F1 | 闪存捕获 | 冷启动 ≤800ms，输入框自动聚焦，离线可用，草稿逐字持久化 |
| F2 | 待处理 inbox | 显示条数，支持删除，一条一条处理，不催 |
| F3 | 收编分析（译写/改写/衍生） | 一个主骨架 + 槽位 + 为什么好 + 病症诊断 + 结合画像的例句 |
| F4 | 立刻造句 | 处理完必须写 ≥1 句才落库；判卷给「像不像母语者会说的」而非打分 |
| F5 | 固定阶梯复习 | `0 / 1 / 3 / 7 / 21 / 60` 天；失败退一格并 8 小时后重来 |
| F6 | 隔日召回题 | 答案默认隐藏；题面不得泄露目标骨架 |
| F7 | 真实使用打卡 | 累计 3 次 + 阶梯到达 21 天 → 标记「已内化」 |
| F8 | 压缩台 | 保留逻辑、约一半长度、提炼 pattern |
| F9 | 会前热身 | 输入「10 分钟后要开会讲 X」→ 给 3 个当场就能用上的骨架 |
| F10 | 句库 | 按状态筛选：待处理 / 在学 / 已内化；可搜索 |
| F11 | Profile | 见 3.3 |
| F12 | 模型接入配置 | endpoint / base URL / api key / model + 连通性自检 |
| F13 | 本地通知 | 每天一条，无到期条目则不发；连续未响应自动降频 |
| F14 | 数据持久化与备份 | SQLite + 每日自动备份 + 一键导出/导入 |

### 4.2 P1（MVP 之后，按顺序）

- F15 系统分享面板闪存（不打开 App 就能存）
- F16 通知内快捷回复直接作答
- F17 原生语音输入 / 朗读
- F18 提示词评测集与回归
- F19 个人病症档案（把重复犯的中文思维习惯聚合成 3~5 条，反复针对性出题）

### 4.3 P2 及以后

- F20 会后回收（日历联动：会议结束 20 分钟后问「刚才有没有卡住的地方」）
- F21 飞书机器人入口（在聊天里丢一句就收编；本地通知已覆盖触达，这里只是便利）
- F22 单向语料导入（把自己写过的英文邮件批量喂进去，反推高频病症）
- F23 多设备（**用户自己的网盘同步 SQLite 文件，不做服务端**）
- F24 输出体检（每月一份：新增骨架、真实使用次数、病症变化）

### 4.4 明确不做（Non-goals，长期有效）

发音评分、语法课程体系、词汇量测试、图谱可视化、embedding 语义检索、社交/排行榜/连续天数、内容库（不自产学习材料，只处理用户自己遇到的语言）、多人协作、账号体系。

## 5. 学习引擎设计（刻意做薄）

原方案的引擎有 admission score 加权、四条 skill lane、strength 衰减、多特征 review priority——**方向对，但在 n=1、每周 3 条的数据量下，约 60 个魔法常数无法校准，等于用随机数假装科学。**

MVP 采用可解释的固定规则：

```
准入：不打分。由用户一句话回答「你以后真的会说这句话吗」——是/否。
      模型只做一件事：如果否，说明为什么它不值得收（太书面 / 太窄 / 已会）。

阶梯：boxes = [0, 1, 3, 7, 21, 60]（天）
      通过 → box+1；失败 → box-1 且 8 小时后重来（不惩罚、不清零）

状态：captured → learning → owned
      owned 条件 = box ≥ 4 且 real_use_count ≥ 3

出题：从到期集合里随机一条。不做优先级排序——到期量小的时候排序毫无意义。
      题型轮换：cued_recall（中文提示说英文）→ pattern_completion（补槽位）→ generation（新场景造句）
```

**升级触发条件（写死，防止提前过度工程）**：当库内 owned + learning 总量 > 150 条，或每日到期量 > 12 条时，才引入优先级排序与遗忘曲线拟合。在那之前，任何调度复杂度都是负收益。

## 6. 成功指标

### 北极星（首页只显示这两个）

1. **已内化骨架数**（owned count）
2. **真实使用次数**（real_use_count 总和）

### 过程指标

| 指标 | 目标 | 说明 |
| --- | --- | --- |
| 捕获延迟 | ≤5 秒 | 从想存到已存 |
| 每周新收编 | 3 条（硬上限） | 少于 2 条说明捕获入口不够顺 |
| 隔日召回完成率 | ≥70% | 低于此说明触达方式有问题 |
| 骨架可用率 | ≥70% | 用户点头「这个我以后肯定会说」的比例 |
| LLM 味误报率 | 0 | 推荐了黑名单风格表达即为 bug |

### 明确不看的指标

打开次数、使用时长、连续打卡天数、收藏数、词汇量。**这些指标越高，往往说明产品越失败**——它要的是短暂接触、高频复用，不是黏性。

## 7. 分期实现路线

### Phase 0 · 原型（已完成）

纯前端 PWA，验证交互形态与提示词方向。产出：可访问的原型 + 设计评审。

### Phase 1 · 装机可依赖（W1–W4）

见 `MVP-TODO.md`。核心是三件事：**数据不丢、只配一个接入点、本地通知立起承重墙**。
出口判据：连续 7 天不主动打开 App 也能完成每日召回。

### Phase 2 · 冷静期（14 天，只用不加）

**这一期最容易被跳过，也最重要。** 不写任何新功能，只记录：

- 每天真的存了几条？（<1 条 → 捕获入口还是太重）
- 骨架里有多少你真的会用？（<50% → 提示词问题，不是功能问题）
- 隔日召回真的做了吗？（<50% → 触达方式错了）
- 有没有一次真实使用打卡？（0 次 → **整个假设有问题，需要重新设计而不是继续加功能**）

三个分叉：
- 都达标 → 进 Phase 3。
- 捕获够多但召回少 → 只优化触达（F16 通知内作答），不加功能。
- 捕获都少 → 说明「主动捕获」这个前提不成立，改做**被动捕获**：从你已有的英文输出（邮件、文档）里反推病症，用户不需要主动记任何东西。

### Phase 3 · 真实闭环（1~2 个月）

F15/F16/F17（系统捕获 + 通知内作答 + 原生语音）、F18（提示词评测集，把质量从「感觉不错」变成可回归）、F19（个人病症档案）。
出口判据：owned ≥ 20 条，且其中 ≥15 条能说出至少一次真实使用场合。

### Phase 4 · 嵌进工作流（3~6 个月）

F20 会后回收、F21 飞书机器人、F22 语料导入、F24 月度输出体检。
此时才可以考虑把「英语学习」这个动作彻底取消——它应该完全消失在工作流里。

### Phase 5 · 长期（6 个月以后，且仅在指标验证后）

F23 多设备（网盘文件同步）、引擎升级（触发条件见 §5）、若确实有第二个用户才考虑抽服务端。
**默认答案是永远不做服务端。**

## 8. 风险与止损

| 风险 | 迹象 | 应对 |
| --- | --- | --- |
| 退化成收藏夹 | 闪存越堆越多，待处理 >20 条 | 收紧每周预算；待处理超 10 条时首页只显示「先处理，别再存了」 |
| 模型给的骨架不实用 | 骨架可用率 <50% | 停功能开发，全力做 F18 评测集；必要时换模型 |
| 真实使用打卡从来没人点 | 打卡数长期 0 | 说明 P5 无法落地，改为「写一句你打算在哪用」的轻量替代 |
| 通知变噪音 | 连续忽略 | 已内置自动降频；再无效则改为**只在你主动打开时出题** |
| 作者自己不用了 | 连续 5 天无任何写入 | 直接归档项目。单用户工具，作者不用即失败，不需要挽救 |

## 附录：为什么这版和原方案的差别在优先级，不在概念

原方案（实习生版）的概念大体是对的：Capture → Normalize → Practice → Recall、骨架化、多场景产出、LLM 只提议不决定状态。它的问题是**优先级配错了**：

- 把移动端、快速捕获、推送、语音**列为 MVP 非目标**——而这四项恰好是「时间稀缺」场景下唯一的杠杆。
- 把复杂调度引擎（60 个不可校准常数）**前置到 MVP**——而它在 n=1 时贡献为零。

一句话总结这份 PRD 做的事：**把杠杆点前移，把复杂度后置，并且给复杂度设定明确的触发条件而不是「以后再说」。**
